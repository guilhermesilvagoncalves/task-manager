# 003 - Task service

## Goal
Authenticated users manage their own tasks. A user never sees or changes another user's tasks.

## Business rules
- A task has title, description, status and due date; all are required.
- Title: 1 to 100 characters. Description: 1 to 500 characters.
  "Character" = Unicode code point (an emoji counts as 1). Leading/trailing whitespace is trimmed before validation.
- Status: `TODO`, `IN_PROGRESS`, `DONE`. Defaults to `TODO` on creation when omitted.
- Any status transition is allowed.
- Due date is a calendar date (`yyyy-MM-dd`) with no temporal restriction (past dates allowed).
- The owner of a task is the user identified by the token; it is never taken from the request body.
- Update is a full replacement (PUT). Last write wins; lost updates are accepted.
- List: page size fixed at 10, first page is 0, sorted by creation date (newest first).
- All task endpoints live under `/api/me/tasks`: the path states that the resource is scoped to the authenticated user.

## Acceptance criteria

### Authentication
- [x] No token, malformed token, expired token or token from another issuer → 401 on every endpoint.
- [x] A valid token issued by the auth service (spec 001) is accepted without calling the auth service per request.

### Create — `POST /api/me/tasks`
- [x] Valid payload → 201 with the task and a `Location` header pointing to `/api/me/tasks/{id}`.
- [x] Status omitted → task created as `TODO`.
- [x] Missing or blank title/description, or missing due date → 400 with the error per field.
- [x] Unknown status or malformed date → 400.
- [x] Title with exactly 100 characters and description with exactly 500 → 201.
- [x] Title with 101 or description with 501 characters → 400 with the error per field.
- [x] Title of 100 emojis → 201 (code points, not UTF-16 units).
- [x] An `owner` field sent in the body is ignored; the task belongs to the token's user.

### Read — `GET /api/me/tasks/{id}`
- [x] Own task → 200.
- [x] Non-existent task → 404.
- [x] Malformed id → 400.

### List — `GET /api/me/tasks?page=N`
- [x] Returns all of the user's tasks, newest first, at most 10 per page, with total count and total pages.
- [x] No `page` → page 0. Page beyond the last → 200 with an empty list.
- [x] Negative or non-numeric `page` → 400.
- [x] Pagination is stable: while the user's tasks do not change, no task appears twice or is skipped across
  all pages, even when tasks share the same `createdAt`. A task created or deleted between two page
  requests shifts the following pages (offset pagination, ADR 014).
- [x] User has no tasks → 200 with an empty list.

### Update — `PUT /api/me/tasks/{id}`
- [x] Own task with full valid payload → 200 with the updated task; `createdAt` unchanged, `updatedAt` changed.
- [x] Any required field missing (including status) → 400.
- [x] Same length rules as Create.
- [x] A task with a past due date can be updated without changing the date.
- [x] Non-existent task → 404.

### Delete — `DELETE /api/me/tasks/{id}`
- [x] Own task → 204; a subsequent GET → 404.
- [x] Non-existent task → 404.

### Ownership
- [x] User B gets 404 (never 403) on GET, PUT and DELETE of user A's task.
- [x] User B's list never contains user A's tasks.
- [x] After B's failed PUT/DELETE, A's task is unchanged.

### General
- [x] Length limits are enforced consistently across layers: any value accepted by the API is persisted
  unchanged, and any value over the limit is rejected with 400, never 500.
- [x] No task endpoint exists outside `/api/me/tasks` (e.g. `GET /api/tasks` → 404).
- [x] Unsupported method → 405; unknown route → 404 (with a valid token).
- [x] Error responses follow RFC 7807, same format as spec 001.
- [x] No blocking calls on the request path.
- [x] Errors generated by the gateway itself (no matching route → 404, downstream unavailable or
  timing out → 502/503/504) follow RFC 7807, same shape as the services' errors.

## Response shapes

### Task
{ "id": "uuid", "title": "string", "description": "string", "status": "TODO|IN_PROGRESS|DONE",
"dueDate": "yyyy-MM-dd", "createdAt": "ISO-8601 UTC", "updatedAt": "ISO-8601 UTC" }

### Task list
{ "items": [Task], "page": 0, "size": 10, "totalItems": 23, "totalPages": 3 }

### Error (RFC 7807, as in spec 001)
{ "type": "...", "title": "...", "status": 400, "detail": "...", "errors": { "field": "message" } }

## Decisions
- Token validation in `task-service` as an OAuth2 resource server with the JWKS fetched once and cached
  (ADR 008). `AUTH_JWKS_URI` = `http://auth-service:8082/.well-known/jwks.json`, `AUTH_ISSUER` =
  `http://auth-service:8082`. The OpenAPI document (`/v3/api-docs`) needs no token; it is not routed
  by the gateway.
- Gateway routes only `/api/me/tasks` and `/api/me/tasks/**` to `task-service`; any other path is a
  404 from the gateway. Errors raised by the gateway itself are RFC 7807 too.
- Title and description are stored trimmed (the value that was validated).
- Column limits: `VARCHAR(100)` and `VARCHAR(500)` in Postgres count characters (code points), so the
  database enforces the same limits as the API.
- Timestamps are truncated to microseconds (Postgres precision), so a response equals a later read.
- Pagination order: `created_at DESC, id DESC` (the id breaks ties).
- Repository tests run on Postgres with Testcontainers (ADR 009).
- The `skeleton` table from spec 001 is dropped by a migration together with `/api/ping`.

## Out of scope
- PATCH (partial update).
- Status transition rules.
- Optimistic concurrency (ETag / If-Match).
- Due date restrictions.
- Filtering, search, client-defined page size or sort.
- Sharing tasks between users; admin views.
